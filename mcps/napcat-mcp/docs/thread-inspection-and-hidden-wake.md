# 对话状态查询与自动提醒的合并维护

本修复将查状态与真正唤醒分开，并保留提醒显示、历史读取和正常请求的回包关系。生产切换在维护窗口进行，准备及隔离测试可以先完成。

## 查状态使用摘要接口

摘要包含对话身份和运行状态，省去逐轮历史。[官方 App-server 文档](https://learn.chatgpt.com/docs/app-server)说明，`thread/read` 可以读取已保存的对话而不恢复或订阅它。

```text
通信桥 inspectThread
    → POST /v1/threads/inspect
    → 既有 Desktop 上游连接
    → thread/read { threadId, includeTurns: false }
    → 返回匹配的 thread 摘要
```

控制接口使用现有鉴权。没有已经初始化的 Desktop 连接时返回 `NO_DESKTOP_CLIENT`，不额外启动连接或恢复对话。查询不写订阅和唤醒账本，不发送 `thread/resume`、`turn/start` 或 `turn/steer`。

| 官方状态 | 通信桥结果 | 查询含义 |
|---|---|---|
| `idle` | `idle` | 当前空闲 |
| `active` | `busy` | 当前仍有活动 |
| `notLoaded` | `not_loaded` | 对话存在，尚未加载 |
| `systemError` | `system_error` | 对话存在，状态报告系统错误 |
| 未识别状态 | `unknown` | 保留摘要和原始状态，等待明确结果 |

官方 `thread.status` 优先于历史轮次状态，旧字符串格式继续支持。摘要的 `thread.id` 必须匹配查询目标，错身份或畸形回包明确失败。能力不支持和存储错误保留原始 RPC 错误；只有指向本次目标 ID、且符合约定错误类型的不存在回包，才转换为 `not_found`。

原有唤醒冷却保持不变，仅 `idle` 可以提前通过空闲核验。`not_loaded` 保留存在性并等待原冷却流程。

## 真正唤醒保持恢复动作

```text
真正 wake
    → 注册本任务订阅
    → thread/resume
    → 核目标身份和当前状态
    → 空闲时 turn/start，已有活动轮时 turn/steer
```

直连通信桥先读取摘要，确认空闲或未加载后显式恢复，再按恢复结果决定是否启动。未知结果保留原请求的账本和去重身份，通过原请求状态核对后处理。

`hidden` 保留从空闲新开一轮的首条提醒，隐藏同轮中途提醒；`visible` 保留全部提醒。模型实际收到的正文和助手回复保持完整，Desktop 重新加载完整历史及分页历史时沿用同一显示选择。显示选择取自对应绑定，调用方传入的其它字段不会代替绑定。

## 请求 ID 与观测保持一致

请求 ID 将回包关联到发起请求的调用方。内部查询使用独立 ID，Desktop 普通请求遇到冲突时重映射，回包恢复为 Desktop 原 ID；内部回包只交内部等待者。

大回包也需要结束请求登记并恢复 ID，同时保持正文处理预算。已启用的对话观测模块只观察归属确认后的 Desktop 回包和相关通知，避免内部查询或重映射 ID 触发错误事件。

## 四文件准备和独立恢复

本次生产目标限定为以下四个文件，依赖文件只验证既有字节。

| 文件 | 作用 |
|---|---|
| `src/codex-app-server-proxy.mjs` | 查询接口、回包归属和提醒显示 |
| `src/codex-thread-bridge.mjs` | 查询、状态解释和真正唤醒 |
| `src/wake-visibility.mjs` | 提醒身份及历史显示 |
| `ops/update-codex-napcat-bridge.ps1` | 更新器的已加载依赖清单 |

公共来源、具体生产基线和部署字节分别记录。两端既有功能不同的情况下，由清单明确机器基线和对应的四文件候选，两端使用同字节的独立维护入口。既有观测功能及其依赖继续保留。

`ops/manage-merged-proxy-candidate.ps1` 默认只读检查；`Prepare` 验证原件并准备逐文件备份；`Apply` 和 `Restore` 需要明确离线窗口，并核对进程、路径、所选机器基线和备份归属。该入口不停止或启动服务，不执行整目录更新器，私有配置、账号绑定及任务账本保持原样。恢复所需资料保存在本机私有备份目录。

`Apply` 核对完整候选和既有依赖。`Restore` 使用归属固定的本机四份原件备份，核对原件哈希、权限及目标已知状态；候选正文损坏或缺失时仍可恢复。未写入的依赖缺失或漂移记在 `dependencyWarnings`，四文件恢复返回 `fourFileResult`，服务调用链继续保留 `chainValidation=PENDING`，由维护任务核验后再恢复运行。

应用前让活动任务保存状态，退出 Codex 并按维护约定停到安全位置。外层与路由分别加载 proxy 和 bridge，重新启动后需要确认两者都加载本次文件，再验证实际消息、读取、去重和精确确认。代码文件替换与进程加载分别验收。

## 验证范围

自动回归覆盖官方状态、错身份和错误回包、并发查询、请求 ID 冲突、大回包、提醒显示与历史投影。实际 App-server 隔离测试使用独立配置目录、动态本地端口和固定响应服务，核对反复查询前后的已加载对话列表、模型请求数和账本，以及新轮、中途提醒、手动输入和历史重载。

准备记录写清使用的官方二进制、文件哈希、依赖和清理结果。真实 Desktop 界面、生产正常退出重开及长运行内存收益，在实际应用窗口继续验收。
