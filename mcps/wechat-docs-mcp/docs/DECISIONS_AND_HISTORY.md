# 决策历史与技术路线

## 1. 已放弃的路线

### 1.1 wxautox4 Plus（付费）

**时间**：2026-08 初
**结论**：能提供接近目标的监听和发送，但关键监听能力付费。当前没有激活，不作为免费主线。

### 1.2 免费 wxauto4

**时间**：2026-08 初
**结论**：当前发行包保留发送和聊天信息能力，但缺少长期监听接口。降级到支持版本也不能补齐监听闭环。

### 1.3 WeChatFerry / WCF

**时间**：2026-08 初
**结论**：绑定旧微信版本，仓库已归档，旧客户端已有无法登录报告。不作为当前主线。

### 1.4 微信 4.1.12.26 被动数据库内存读取

**时间**：2026-08 初
**结论**：四类受控实验只取得 `session.db`，联系人和消息数据库始终不可用。

四类实验详情：

| 实验 | 操作 | 结果 |
|---|---|---|
| 1 | 完全退出后重新登录 | 捕获到 `session.db`，但没有 contact/message |
| 2 | 登录后依次打开两个授权会话 | 没有新增有效数据库能力 |
| 3 | 退出前保持授权群选中，再重新登录恢复 | 没有新增有效数据库能力 |
| 4 | 从另一账号向授权群发送唯一新消息 | 10 个文件变化，但仍没有新的可用 contact/message 能力 |

**关键发现**：第四类实验证明真实新消息能提供可靠的本地文件活动边界，但文件变化本身不能告诉我们是哪个 route，也不能提供消息正文。因此数据库文件变化只能作为"门铃"，不能作为消息读取器。

### 1.5 Windows UI Automation (UIA) 路线

**时间**：2026-08 中
**结论**：作为"门铃 + UIA 读取"混合方案的读取层尝试过，但 UIA 树不暴露足够的语义信息来可靠地提取消息内容。旧 UIA 文档（`WINDSURF_HANDOFF_20260809.md` 和 `plans/stage-2-ui-observation.md`）保留为历史探索记录，已被当前数据库解密路线取代。

## 2. 当前路线：WCDB 解密 + SQLite 轮询

### 2.1 为什么放弃 UIA 转向数据库解密？

| 因素 | UIA 路线 | 数据库解密路线 |
|---|---|---|
| 数据完整性 | 依赖 UI 树语义，部分消息类型无法提取 | 直接读数据库，所有消息类型可提取 |
| 稳定性 | 受窗口状态（最小化/锁屏）影响 | 不依赖窗口状态 |
| 发送者信息 | UI 树可能不暴露真实 wxid | 数据库有完整的 username 映射 |
| 维护成本 | 微信 UI 变化会破坏 UIA 树结构 | 数据库结构更稳定 |
| 附件元数据 | UI 树通常只有文件名 | 数据库有完整的大小、类型信息 |

### 2.2 raw key 扫描为什么失败？

早期尝试直接在微信进程内存中搜索 32 字节随机密钥：

1. 微信 4.1+ 不再把 raw key 以连续字节存储在固定位置
2. WCDB 使用 `Config.Cipher` 结构管理密钥，包含派生密钥和加密参数
3. 直接搜索 32 字节序列会产生大量误报
4. 即使找到候选密钥，也无法确定它对应哪个数据库

### 2.3 Config.Cipher 扫描为什么成功？

`Config.Cipher` 是 WCDB 内部的密钥管理结构，有固定的内存布局特征：

1. 包含派生后的数据库密钥（32 字节）
2. 包含加密参数（页大小 4096、KDF 迭代 256000 等）
3. 包含数据库文件路径映射

通过扫描这个结构的特征模式（而非搜索随机密钥），可以精确定位所有 18 个数据库的密钥，实现 18/18 解密。

### 2.4 为什么用 zstd 而非其他压缩？

微信 4.1+ 选择 zstandard 压缩较长消息内容的原因（推测）：
- zstd 解压速度快（~1GB/s）
- 压缩率高于 zlib
- WCDB 内置支持，`WCDB_CT_*` 字段标志压缩类型

本系统通过 `zstandard` Python 包解压，`WCDB_CT_message_content=4` 时调用 `ZstdDecompressor.decompress()`。

## 3. 架构决策记录

### 3.1 为什么用 SQLite 而非 JSONL？

- **事务性**：SQLite WAL 模式保证崩溃恢复
- **查询能力**：可按 route、时间、状态过滤
- **去重约束**：`UNIQUE(route_id, source_fingerprint)` 数据库层面保证
- **并发安全**：`BEGIN IMMEDIATE` 事务防止竞态
- JSONL 只作为审计副本，由 SQLite 事务生成

### 3.2 为什么用 contiguous baseline 而非 max baseline？

**问题**：消息 4 成功、5 失败、6 成功时，max baseline 推进到 6，第 5 条永久丢失。

**解决**：contiguous baseline 从前往后扫，遇到第一个失败就停止。基线停在 4，第 5 条下轮重试，第 6 条靠 `source_fingerprint` 去重。

### 3.3 为什么快照延迟推进？

**问题**：如果解密成功后立即推进快照，但入账失败，下一轮不会重试。

**解决**：快照只在**全部成功**后推进。任何步骤失败都保留旧快照，下轮自动重试。已入账的消息靠 `source_fingerprint` 去重，不会重复入账。

### 3.4 为什么每代线程用独立停止事件？

**问题**：共用一个 `threading.Event`，`wechat_poll_start` 的 `clear()` 会让旧线程复活。

**解决**：每代线程创建独立的 `Event`，旧线程的 `Event` 永远不会被 clear。`wechat_poll_stop` 超时时保留线程引用，不允许新线程启动。

### 3.5 为什么用 SQLite backup() 而非 shutil.copy2？

**问题**：WAL 模式的 SQLite 主文件可能不包含最新事务（在 -wal 文件中），`shutil.copy2` 只复制主文件会丢失数据。

**解决**：`sqlite3.connect(src).backup(dst)` 是 SQLite 原生 API，正确处理 WAL 模式，保证备份一致性。
