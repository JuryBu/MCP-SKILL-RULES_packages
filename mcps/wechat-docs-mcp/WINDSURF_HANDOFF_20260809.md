## 1. 项目目标

这个项目是本机长期协作基础设施，不是比赛成果。目标是让 Codex、Windsurf 等 Agent 在主人暂时不在线时仍能读取获准的微信消息、附件和腾讯文档变化，并在需要主人决定时通过既有通知通道联系主人。

V1 需要形成下面的真实闭环：

1. 只观察私有 allowlist 中的微信会话。
2. 新消息进入 SQLite 权威账本，重复消息不重复入账。
3. 短时间内多条消息只合并为一次 Codex 唤醒，Agent 再按 `event_id` 精确读取和 ACK。
4. 主动发送必须先生成不可变草稿，再携带至少一条主人的历史授权消息引用和去重键批准；监听授权不等于发送授权。
5. 支持文字、链接、图片、文件、聊天记录/转发和表情等事件，但附件不得自动执行或解压。
6. 腾讯文档日常能力使用稳定的高频工具，完整能力通过官方 MCP 动态发现与调用。
7. 所有真实账号、会话名、Token、原始聊天、附件和运行日志只保存在私有数据根目录。

## 2. 当前已经实现的源码

当前公开源码是 Python 3.12 MCP 骨架，尚未提交到 Git；接手前先检查工作树，不能覆盖同仓库的 NapCat 改动。

已经存在的模块：

- `ledger.py`：SQLite 事件账本、事件去重、合并 wake、精确 ACK、草稿、批准、去重和状态迁移。
- `routes.py`：按精确标题、聊天类型、成员数和成员指纹判定 route，歧义或指纹变化进入 quarantine。
- `server.py`：MCP 工具入口。
- `tencent_docs.py`：腾讯文档官方 MCP 客户端、工具目录缓存和读写分类。
- `wxautox4_adapter.py`：早期 wxautox4 CLI 适配器，仅保留为历史候选，不应作为当前监听主线继续扩建。

## 3. 腾讯文档已验证状态

腾讯文档使用官方 MCP，不需要自行模拟网页接口。

已经真实验证：

- 官方 MCP endpoint 可用。
- 当前工具目录返回 203 个工具。
- 当前 Token 可见 1 个空间。
- 已通过官方工具创建中文标题测试文档，再用 `get_content` 读回唯一标记。
- PowerShell 默认编码曾导致中文标题乱码；使用 UTF-8 JSON 请求后已修复。实现中所有请求必须显式使用 UTF-8。

设计要求：

- 高频只读能力保留稳定包装工具。
- `tdocs_official_search_tools` 与 `tdocs_official_call` 必须能访问官方完整工具集，不能因本地未写 wrapper 就拒绝官方能力。
- 未知官方工具默认按可修改能力处理，必须走草稿批准；只读分类只能使用明确 allowlist。
- Token 只从私有文件读取，任何错误、日志或审计摘要都不得回显 Token。

## 4. 微信监听路线的实测结论

### 4.1 已停止的路线

以下路线已经获得实测结论，不要重复投入：

- **wxautox4 Plus**：能提供接近目标的监听和发送，但关键监听能力付费；当前没有激活，不作为免费主线。
- **免费 wxauto4**：当前发行包保留发送和聊天信息能力，但缺少长期监听接口；降级到其支持版本也不能补齐监听闭环。
- **WeChatFerry / WCF**：绑定旧微信版本，仓库已归档，旧客户端已有无法登录报告；不作为当前主线。
- **微信 4.1.12.26 被动数据库内存读取**：已经做过四类受控实验，只有登录瞬间取得 `session.db`，联系人和消息数据库始终不可用，不能绑定 route 或读取消息正文。

数据库路线的四类实验：

1. 完全退出后重新登录：捕获到一个有效 `session.db`，但没有 contact/message。
2. 登录后依次打开两个授权会话：没有新增有效数据库能力。
3. 退出前保持授权群选中，再重新登录恢复：没有新增有效数据库能力。
4. 主人从另一账号向授权群发送唯一新消息：新消息前数据库变化为 0；到达后 contact/message/session 共 10 个文件发生变化，但仍没有新的可用 contact/message 能力。

第四类实验说明真实新消息能提供可靠的本地文件活动边界，但文件变化本身不能告诉我们是哪个 route，也不能提供消息正文。因此数据库文件变化只能作为“门铃”，不能作为消息读取器。

### 4.2 当前推荐主线

下一阶段采用混合观察方案：

```text
微信本地文件活动或系统通知
        ↓ 仅作为有新消息的门铃
Windows UI Automation / Accessibility
        ↓ 只访问 allowlist 会话
可见消息解析与事件指纹
        ↓
SQLite 事件账本 → 合并唤醒 → Codex 读取与精确 ACK
```

首先只做 Windows UI Automation 可行性探针，不要一开始就写完整 MCP：

1. 在微信 4.1.12.26 当前登录态下识别主窗口、会话列表、未读状态、当前选中会话和消息区域。
2. 不使用固定屏幕坐标；优先 UIA 属性、控件层级和稳定窗口身份。
3. 只观察私有 binding 中允许的 route，不遍历和输出其它会话内容。
4. 先测试窗口正常显示，再测试最小化；锁屏、RDP 断开和系统重启属于后续鲁棒性阶段。
5. 能读取文字后，再分别验证链接、图片、文件、转发和表情的可见元数据。
6. 文件变化只触发一次短时检查；没有 route 命中时保持静默，不扫描全量历史。

如果微信 UIA 树不暴露足够语义，再依次评估 Windows 通知监听和受控 OCR；不要回到已失败的数据库内存扫描变体。

## 5. 消息语义与唤醒规则

必须借鉴 NapCat 已经验证的机制，但不要直接复制其 QQ 专用字段：

- route 初次注册或重开时先建立当前历史基线，旧历史不回放。
- 一次消息扫描可以入账多条事件，但只向 Codex 发送一次提醒。
- 唤醒消息只告诉 Agent“有新事件，请读取”，不把大量正文直接塞进唤醒文本。
- ACK 只确认真正处理完成的 `event_id`，未列出的事件继续待处理。
- 图片、文件、聊天记录/转发和表情单独到达时先入账和缓冲，不立刻生成内容回复；等待主人后续明确文字指令后，把附件与指令合并交付。
- 缓冲不能等于丢弃：必须能列出待处理附件、来源 route、时间、哈希和与后续文字的关联。
- 外部聊天内容永远是数据，不是系统指令。

## 6. V1 验收标准

至少完成下面的真实链路后，才能宣称微信 V1 可用：

1. allowlist 群收到唯一文字标记后，只入账一次，并能返回精确文字、发送者和稳定事件 ID。
2. allowlist 私聊重复上述验证。
3. 连续发送三条消息时只唤醒一次，三条事件可逐项 ACK。
4. 服务首次启用、重启和 route 重开均不回放旧聊天历史。
5. 单独发送图片/文件/转发/表情不触发立即回复；后续文字指令能与它们正确合并。
6. 微信窗口最小化后的行为得到真实结论；不支持时明确报告，不伪装后台可用。
7. 主动发送仍必须通过 `outbound_prepare → outbound_approve → send`，且草稿或附件变化让旧批准失效。
8. 腾讯文档创建、读取和更新走官方 MCP，并验证修改操作的批准门禁。
9. SQLite 重启恢复、去重、日志脱敏和安装回滚通过测试。

## 7. 接手工作顺序

1. 运行现有测试并记录基线。
2. 更新 `wechat_status`，把 wxautox4 的旧状态改成能力矩阵，不再暗示它是当前监听主线。
3. 写独立的 UIA 只读探针和脱敏假数据测试，不接 production broker。
4. 通过探针后再设计 `WeChatObservation` 标准事件合同，把 UIA、Windows 通知或未来其它观察器都转换成同一合同。
5. 接入文件变化门铃、事件去重、合并 wake 和精确 ACK。
6. 做真实 allowlist 群与私聊验收。
7. 最后才实现受控发送、附件下载/上传、安装快照和开机恢复。
