# Stage 2：微信界面观察与真实入站闭环

> **⚠️ 历史归档文档**
>
> 本阶段计划基于 Windows UI Automation (UIA) 路线。该路线已被当前 **WCDB 解密 + SQLite 轮询** 路线取代。当前路线通过 `Config.Cipher` 内存扫描提取密钥，解密 `message_0.db` 和 `contact.db`，直接读取消息而非通过 UIA。
>
> 保留此文档作为历史探索记录。当前路线请参阅 [README.md](../README.md) 和 [docs/](../docs/) 目录。

## 目标

在不依赖付费 wxautox4、旧版 Hook 或数据库内容解密的前提下，验证微信 4.1.12.26 是否能通过 Windows UI Automation 读取私有 allowlist 会话的新消息，并将结果转换为统一事件合同。

## 实施边界

- 第一阶段只读，不发送、不点击输入框、不滚动历史、不修改微信文件。
- 不使用固定屏幕坐标作为主定位方式。
- 数据库文件活动或 Windows 通知只能作为唤醒门铃，不能直接推断 route 或消息内容。
- UIA 探针只保留控件类型、稳定属性和 allowlist 命中结果，不输出其它会话标题或正文。
- 不接 production broker，不修改 NapCat 生产运行态。

## 阶段步骤

1. 盘点微信窗口、进程和 UIA 树。
2. 验证会话列表、未读状态和消息区域是否可读。
3. 定义 `WeChatObservation` 标准事件合同与脱敏夹具。
4. 用 allowlist 群的唯一新消息做真实只读验证。
5. 用 allowlist 私聊重复验证。
6. 接入 SQLite 去重、合并 wake 与精确 ACK。
7. 验证首次基线、重启和 route 重开不回放旧历史。
8. 验证图片、文件、转发和表情的缓冲等待规则。

## 成功标准

- 群和私聊各有一条真实新消息被唯一识别并只入账一次。
- 不需要读取数据库明文或扫描非 allowlist 会话历史。
- 三条短时连续消息只触发一个 wake，仍生成三个可精确 ACK 的事件。
- 首次启用和重启后不回放既有历史。
- UIA 在正常窗口和最小化状态的实际能力边界有证据。

## 止损条件

- UIA 树不暴露会话和消息语义，且 Windows 通知无法提供 allowlist route 身份时，停止直接 UIA 主线，转入受控 OCR 可行性评估。
- 不再重复登录瞬间、打开会话或数据库内存扫描实验，除非出现实质不同的上游技术或客户端版本变化。
