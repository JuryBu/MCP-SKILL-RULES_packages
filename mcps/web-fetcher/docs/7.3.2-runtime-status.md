# 7.3.2 空闲状态与自动唤醒诊断

## 日常使用

非 Antigravity LS 环境中，连续一小时没有工具活动且没有执行中的请求，后端会清理资源并退出。共享 broker 在下次普通调用时重新启动后端。浏览器空闲二十分钟释放内存的策略保持原样，本次只补充状态说明与诊断。

| 入口 | 用途 | 是否启动后端 |
| --- | --- | --- |
| `npm run runtime:status` | 从组件安装目录读取本机记录 | 否 |
| `web_list_sessions` | 同时查看会话、页面池和当前运行状态 | broker 可能按需启动 |
| `web-fetcher://runtime` | 读取当前进程的结构化诊断 | broker 可能按需启动 |

只读命令须在实际安装目录执行，也可用本机 Node 运行该目录的 `scripts/runtime-status.mjs`。未构建源码时先运行 `npm run build`。状态文件默认按安装位置和父进程隔离，放在系统临时目录；明确配置 `WEB_FETCHER_RUNTIME_STATE_FILE` 时使用指定文件，该文件应由同一受信任维护入口独占。

## 状态含义

| 状态 | 含义 | 建议动作 |
| --- | --- | --- |
| `sleeping` | 已记录按一小时空闲规则退出 | 正常调用即可由 broker 唤醒 |
| `starting` / `ready` | 启动中 / 已建立 MCP 传输 | 等待初始化 / 正常使用 |
| `startup-failed` | 启动流程捕获到失败 | 查看本机启动日志，修复后再调用 |
| `stopped` | 已记录标准输入关闭、父进程退出或信号等原因 | 按 `reason` 核对宿主与进程 |
| `unknown` 或无记录 | 进程已消失但未写退出记录，或文件缺失、损坏 | 核对日志与实际安装目录 |

只读命令会标记观察到的 PID 存活情况。保存的 `ready` / `starting` 对应 PID 已消失时，显示 `unknown` 和 `unobserved-exit`，保留原始时间。记录无法覆盖断电、强杀、加载模块前失败或系统清理临时目录的全部情况。PID 存活观察也受系统权限和 PID 复用影响。

全局 `broker-state.json` 的 `connected=false` 仍只表示连接已断开；组件的空闲原因通过以上入口查看。本次没有修改共享 broker 的状态文件格式、启动策略或其它组件。

## 工具结果与耗时

工具结果新增 `_meta.webFetcherLifecycle`，保留原有 content 和其它 `_meta` 字段。只有读到同一父进程的上一条 `idle-timeout` 退出记录，首个成功工具结果才追加一次唤醒说明；错误结果保留这次提示机会。多请求并发完成时，只有一个成功结果获得提示，原有图片与文本顺序保持。

`startupMs` 从 Node 进程启动计时到 MCP 传输就绪，包括模块加载与启动探测；broker 排队、网络往返和页面操作时间沿用各自计时。缺少上一条记录时正常返回结果并提供当前诊断，不推断退出原因。

Cookie / localStorage 备份仍保留，登录是否有效应访问目标页面确认。进程内的网页会话、人工验证任务和桌面附着对象会随原有退出流程清理，重启后需重新取得对应 ID；不会自动重放点击、输入等动作。

状态持久化失败时，原工具仍正常运行，当前诊断的 `persistence` 显示 `unavailable`。检测到另一个实例持有同一路径时显示 `other-instance`，当前实例停止覆盖该记录。

## 维护验证

`npm run test:runtime-status` 覆盖状态转换、坏文件、写入失败、实例隔离、并发提示及 content 保留。`npm run test:runtime-status:integration` 使用隔离临时目录和受控时钟，在真实 stdio MCP 入口验证退出与重新连接；正式环境的一小时策略保持原值。`npm run test:contract` 核对33个工具、原参数和新增资源。
