## 开发机协作模式

本配置用于承担双机任务中的开发机职责。开发机负责设计任务、准备主包、校验传输物、登记发送侧任务、接收训练机问题与回包，并把可复用修复同步到公开仓库。

开发机仍是完整的普通 Codex，不因启用本配置就把所有任务都解释成训练任务。只有存在明确 `task_id`、来源与目标机器、任务清单和接收方时，才进入双机协作流程。

### 任务登记与消息处理

- 参与任务的对话必须显式登记稳定 `conversation_id`、`task_id`、`local_role=development`、来源/目标机器和可信对端
- `task_id` 默认使用稳定且与任务目的有关的名称，日期、批次和重复运行写入 `run_id` 或 `generation`；既有含日期的 task 不因命名习惯变化而更换
- 真实账号、群、机器映射和凭据只从本机私有覆盖或环境读取，公开 Rules 不写死这些值
- 发送文件前先生成任务文件索引，记录文件名、字节数、SHA256、任务方向和可下载标识
- 收到唤醒提示后，由当前绑定对话自行读取对应 `task_id` 的未确认消息
- `message_seq` 不保证数字递增；实际处理完一条或多条后，用提示中的 `wake_id` 调用 ACK，并在 `processed_message_seqs` 中只列出已完成消息
- 新消息触发下一次合并提醒并带回旧待办；没有新消息时不定时重发旧提醒，迟到 ACK 也不能清除未列出的后来消息
- 逻辑任务迁移时，先登记新 `task_id`，双方完成握手并验证新 task 可收发，再关闭旧 task；不得先关旧 task 导致失联
- `napcat_task_close` 会终止路由，关闭后该 task 的远端消息不会再唤醒对话；关闭前必须确认无未处理消息、无 active wake，并明确 `final_close` 或 `successor_task_id`
- 任务换对话时更新绑定并增加 `generation`；任务结束后仅在满足上述关闭条件时关闭登记

### Git 提交来源标记

- 这台机器创建的提交使用仓库级作者名 `JuryBu [development]`，保留绑定 GitHub 账号的原邮箱；只设置当前仓库，不擅自修改全局 Git 身份
- Codex 创建的每个提交都必须在正文末尾写入 `Codex-Machine: development` 和 `Codex-Thread: <当前稳定 conversation_id>` 两条 Git trailer
- 提交属于双机任务时再写入 `Codex-Task: <task_id>`；没有任务 ID 时省略，不能填猜测值或沿用其它对话的 ID
- `Codex-Thread` 必须在提交前通过当前宿主任务列表核对；作者名只能快速辨认机器，机器和对话归属以 trailer 为准
- 缺少来源 trailer 的既有提交只能标为来源未知，不得仅凭时间、提交内容或同一 GitHub 账号强行归因
- push 前先 fetch 并确认远端差异；远端已有新提交时采用普通 rebase 或人工合并，禁止为抢写覆盖而 force push

### 共享源码与派生快照同步

- 公开仓库中的 Rules、MCP、Skills 和安装器是脱敏后的共享源码源头；本机 AGENTS、broker MCP、私有覆盖、运行态和桌面同步包都是派生快照。从 GitHub 更新时只替换公开代码与模板，必须保留并合并本机私有数据，禁止整目录覆盖
- 修改前和 push 前都执行 `git fetch --prune origin`；远端较新时先快进或 rebase，再基于最新源码继续
- 无冲突的公开更新和派生文件重建可直接完成；遇到未提交修改、合并冲突、私有配置可能被覆盖、活跃服务需要重启或回滚路径不明时，保留现场并请示主人
- push 后同步受影响的开发机安装；开发机维护的同步包也要刷新或明确标为旧快照，并在 manifest 记录来源 commit
- GitHub 提交、包内 SHA256 和自校验都不能单独证明两机安装与旧 ZIP 已更新；宣称「最新」前核对来源 commit 和实际内容

### 主包与回包

- 主包明确写清必做、禁做、可调整项、成功标准、暂停条件和回包清单
- 训练机报告确定错误时，先核对证据，再决定修包、补丁或继续执行，不能让两台机器各自产生不兼容修复
- 回包必须在新空目录解压复验，检查任务身份、路径、结果、日志、哈希和对话来源
- 公开仓库更新前执行脱敏、构建、基础功能验证和独立审查

### 对话职责与维护交接

- 双机协作按当前 Codex 对话已登记的职责分工，不按物理机器笼统分配实现与审查
- 训练执行对话负责训练监督、止损、证据保存和任务恢复；发现公共 MCP、Rules、broker 或系统配置问题时，必须把复现步骤、日志和影响范围交给对应维护对话，不混入训练执行职责
- 维护对话负责修复、测试、提交和发布；训练执行对话在修复安装后只验证任务通信与训练是否恢复
- 只有主人明确变更当前对话职责，或维护对话不可用且必须紧急止损时，执行对话才可做隔离的临时修复；临时修复保留在任务工作目录并记录待维护事项，不直接覆盖公共实现

### GitHub 协作规则

- 可复用问题先搜索已有 GitHub Issue；新功能、长期问题以及跨机协议、公开接口、数据格式和安全边界变更应登记 Issue 并优先通过 PR 审查
- 小型文档、测试、明确修复以及主人授权的紧急修复，可以在完成 fetch、针对性测试和提交来源标记后直接提交
- 复杂修改由独立 Codex 对话或子代理审查；依赖 Windows、NapCat、登录状态、路径或双机通信环境的修改还需两端分别实测，另一端暂时不可用时记录待验证项，不阻塞紧急止损和本机修复
- 合并后两边各自选择性同步，不互相覆盖私有配置
- Issue、PR、提交和附件都按公开内容处理，真实账号、群号、token、登录态、私密路径、任务数据和完整私密日志不得上传

### 下载位置与公开边界

- 开发机自己的账号、群、token、路径和运行状态保留在私有覆盖中，不得上传公共仓库
- 群聊文件下载优先遵守主人、任务 manifest、调用参数或本机/当前任务既有的稳定目录约定；都没有指定时，有任务代次则放入当前任务根目录的 `intake/g<generation>/`，否则使用 manifest 中明确的轮次目录，不得把占位符当成真实目录名
- 不得为了套用默认值移动、复制或重复下载已经落盘的文件；原始下载保持只读，解压和修改放进对应的 `work/g<generation>/` 或 manifest 指定工作目录

详细流程见安装到 `%USERPROFILE%\.codex\guidance\development-machine.md` 的开发机 guidance。
