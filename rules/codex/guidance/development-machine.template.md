# 开发机双机协作手册

## 适用范围

本手册的双机流程只在存在明确双机任务时生效；「Git 提交来源标记」适用于本机每个 Git 提交，不受双机条件限制。日常开发、文档、检索和普通工程任务不因此进入双机流程。

## 私有覆盖

公开仓库不保存真实账号、群、机器映射、token 和运行路径。安装后由接收者创建私有覆盖文件或环境变量，至少提供：

- 本机逻辑角色与机器名称
- 对端逻辑角色与机器名称
- 本机 NapCat 账号与可信对端账号
- 固定群 ID、群名和预期成员数
- OneBot URL、token 与本机运行目录

缺少这些值时，只允许预览、只读检查和人工传输，不启用自动发送或定向唤醒。

固定群需要迁移时，两端先约定带时区的绝对切换时间。切换前短暂停止结构化发送，读取并处理旧群待确认消息；备份私有 binding 后在约定时刻原子替换群 ID、群名和预期成员数，不关闭或重登记现有任务。切换后核对账号、群身份、路由和 open task，失败立即恢复备份。

## 主包准备

主包必须包含稳定 `task_id`、项目身份、目标机器、文件清单、SHA256、必做项、禁做项、允许调整项、暂停条件、完成条件和回包要求。`task_id` 表示长期协作身份，重复运行的日期、时间和批次放进 `run_id` 或 generation，不因一次重跑就更换任务 ID。

开发机在发送前从新的空目录复验主包，确保没有混入登录态、对话数据库、浏览器 profile、运行日志、旧任务产物和无关大文件。

## 通信协议与显示

任务登记、精确ACK、回执、文件传输、迁移、通知和hidden/visible语义统一遵循同目录 communication-bridges.md，相关操作前必读；本手册不再维护第二份协议。

## 部署与恢复

升级准备、无感热切、回退、启动与重启后恢复的通用要求统一遵循同目录 maintenance-upgrades.md，执行前必读。本手册只补充双机协议状态，不重复另一套通用升级流程。

公共 MCP、Rules 或 broker 的开发、构建、测试、打包和对端影子验证在隔离环境完成，不拿生产任务作测试夹具。正式切换前核对不可保护的 in-flight scan、active wake、task绑定与私有账本；只暂停确有必要的后端，不把长测或跨机等待串进生产停机。

涉及 Codex 退出或整机重启时，核对激活器的 activated/pendingActivation/restartCodexRequired 最终状态、task-router.stop 和自有维护标记已清除，撤销或超时会恢复 router。Windows 登录后共享 broker 应通过包内 Node 绝对路径启动，随后验证 router 连续扫描、open task 与私有账本完整；不能清理他人维护租约。

## 问题回收

训练机报告问题时，开发机先区分任务包错误、环境差异、运行故障和 MCP 工具缺陷。能够继续科学任务时，不让工具缺陷无故阻塞训练；需要修复时由一个维护源统一修改并重新发版，禁止两台机器各补一套不兼容代码。

## 对话职责与维护交接

双机协作按对话职责分工。训练执行对话负责训练监督、止损、证据保存和任务恢复；开发机或训练机的维护对话负责公共 MCP、Rules、broker、安装器和系统配置的修复、测试、提交与发布。

训练执行对话发现基础设施问题时，提供可复现步骤、错误日志、相关消息序号、任务影响和已经采取的止损措施，再交给维护对话处理。主线可在整体任务授权内自主调整主辅职责，但公共基础设施的修改仍由明确承担维护责任的任务集中处理，不能让各执行任务一边监督长跑一边私改、私发共享服务。维护任务不可用时只能按已授权的应急止损范围保全现场或做隔离临时修复，记录并交回维护源。

复杂修改由独立 Codex 对话或子代理审查。依赖 Windows、NapCat、登录状态、路径或双机通信环境的修改还要在两端分别实测；另一端暂时不可用时记录待验证项，可以先发布已完成本机验证的紧急修复。

## 文件下载与工作副本

目录优先级、附件索引字段与完整性验证统一按 `communication-bridges.md` 的「文件与附件」执行。没有明确目录约定时先用系统临时目录，manifest已指定的intake/work代次目录则沿用；不为整理重复下载或移动原件。原始包只读，解压、修改和验包使用工作副本。

## Git 提交来源标记

所有本机提交先按 `maintenance-upgrades.md` 的「Git 提交来源与身份」核对身份、范围和来源。开发机的 `Codex-Machine` 为 `development`，作者名使用本机私有覆盖已确认的 Git 显示名加 `[development]`；保留绑定邮箱，不擅改全局身份。

本节的机器标记不以登记双机任务为前提；`Codex-Task` 仍只填写真实双机任务，不能把普通工程变成双机任务。

## GitHub 协作

可复用问题先搜索已有 Issue。新功能、长期问题以及跨机协议、公开接口、数据格式和安全边界变更应登记 Issue 并优先通过 PR；小型文档、测试、明确修复以及主人授权的紧急修复，可以在完成 fetch、针对性测试、来源标记和脱敏检查后直接提交。

## 发布与两机同步

每个维护仓库使用明确的远端映射，操作前核对当前 remote、分支、工作树和修改归属；修改前与 push 前都执行 `git fetch --prune origin`，远端有新提交时正常合并或 rebase，不 force push。已有无关修改不要一并提交，也不要因看到未提交文件就自动把整项任务交给主人；先隔离自己的更改，所有权冲突无法安全解决时保留现场并说明。

在已授权维护职责内，完成验证和独立审查后主动 commit/push 脱敏的公共修复，记录公开提交及其覆盖范围。同步包写明来源 commit、文件清单与哈希，旧包更新或明确标旧。安装器与规则分层必须保留本机私有覆盖，不整目录替换机器身份、账号、token、绑定和任务账本。

开发机本机安装、公开仓库发布、训练机安装及其运行验收是不同状态，分别登记。训练机通过已登记维护任务接收脱敏包或精确 commit，按其本机私有身份与可用窗口选择性安装；不得复制开发机私有 AGENTS 或用远端消息扩大权限。对端不可用时明确待同步，不重复发送、不把公开提交或包哈希当成双端已生效。

## 回包验收

回包在新空目录解压，逐项核对任务身份、对话身份、运行配置、结果、日志、checkpoint、指标、哈希和主包要求。发现缺失、污染或错对话导出时停止发布，保留证据并要求补包。

通过验收后再进入公开仓库维护流程，执行脱敏、构建、测试、独立审查、commit 和 push。
