# 多模态原生直读、网页预览与视觉验收（Antigravity 2.0）

本专题遵循全局 `GEMINI.md`「专题阅读入口」：处理多模态媒体（图片 / 视频 / 音频 / 大 PDF），或开展浏览器交互、登录墙处理、本地文件（Office / PDF / SVG / HTML）预览、截图与视觉验收前读取。MCP 参数细节配合 `tools-reference` Skill。

## 一、工具分工、内置 `browser` 边界与「读内容 vs 验渲染」分界

1. **三层工具选择与内置 `browser` 防死循环**：
   - **静态公开资料**：首选 `exa.web_search_exa` / `web_fetch_exa`（未配置或不可用时说明原因降级 `search_web`）。
   - **登录态读取、DOM/JS 检查、批量截图与可控自动化**：优先使用 MCP `web-fetcher`（`web_fetch_screenshot`、`web_inspect`、`web_interact`、`web_pipeline`；需操作本机浏览器时切勿粗暴 `taskkill` 用户正在使用的浏览器进程抢 profile 锁，优先用 `web-fetcher` 独立上下文或 `web_human_browser_*` 安全附着）。
   - **内置可视化 `browser` 子代理边界**：仅在明确要求于 IDE 内置浏览器面板实时演示/操作网页应用时委派。注意内置 `browser` 默认使用 Flash 系模型，易在模糊目标下陷入重复 `Wait` 死循环——**派发时严禁给开放式主观分析任务，必须给出精确动作序列与硬性终止条件（如「点击 X 并看到 Y 出现后立即截图返回，最多重试 2 次」）**，收到结果必核对宿主 `BROWSER_HOST_FACTS`。
2. **「读内容图表」与「验排版实际渲染」分清（Office 严禁转 PDF）**：
   - **读内容与图表（单次 `<= 10` 页且 `<= 5 MB` 的 PDF、小图、短音视频）**：直接用内置 `read_file` 原生直读，发挥 Gemini 原生视觉与听觉一次吃透图文图表、运动画面与音轨的优势（大件按第二节分层处理）。
   - **验排版实际渲染（Word、PPT、Excel、需核真实浏览器/页面排版渲染的 PDF、SVG 与本地 HTML）**：一律用 `web-fetcher` 直接通过 `file://` 协议原生打开截图与检查，**严禁把 Office 文档先转 PDF 再验收**。
   - **LibreOffice 并发禁忌**：严禁并发调用 LibreOffice 渲染 Office 截图（争抢配置目录会报 `EPERM`），必须串行逐份渲染，首次冷启动留足约 `45s` 窗口。

## 二、Gemini 原生多模态分层铁律、截图真实性与宿主机防卡护栏

1. **看图说话，禁盲报通过**：拿到截图或分片后必须用 `read_file` 逐张查看画面（IDE 图片单边硬上限 `<= 8000px`；`web-fetcher` 长图默认 `1600px` 分片、`300px` 重叠，按顺序看全不漏页）。`web_inspect` 零告警仅作几何测量初筛，仍须逐张肉眼核实遮挡、溢出、过曝泛白与审美质感。
2. **多模态原生直读与全量请求体分层减体铁律（防每轮重传越传越慢，严禁误退化纯文本、压糊或改坏交付原件）**：
   Antigravity 客户端每轮请求都会把当前会话已 `read_file` 读入的图片、视频、音频与 PDF 二进制随全量请求体重复上传；既要充分发挥 **Gemini `read_file` 原生直吃图片、视频（运动画面+音轨）、音频与 PDF（逐页渲染图+文字层）** 的多模态天赋，又要防止超大原件滚雪球拖慢每拍上传。严格执行五条分层纪律：
   - **① 小件与聊天框已传附件直接用（禁另存重读）**：用户已在聊天框直接附件传入的媒体已在当前历史请求体中，直接观看分析，**严禁另存磁盘后再二次 `read_file` 加倍占位**；单次小件（单图 `<= 400 KB`、音视频 `<= 8 MB`、PDF `<= 10` 页且 `<= 5 MB`）直接用 `read_file` 原生直读，不画蛇添足做预转换。
   - **② 图片（单图 `> 400 KB` 或多图复看）**：用 Python `PIL`（兼容环境下保持 `PYTHONUTF8=0` 且不加 `-S`）在 `scratch/` 生成检视副本——**UI/代码/细小文字截图用无损 WebP（`lossless=True`，防 4:2:0 色度子采样糊字），实拍/3D/海报/平滑渐变图用高质 WebP（`quality=88～92`）**，剥离冗余 EXIF/XMP 非色彩元数据（含非 sRGB ICC 先转 sRGB 防偏色），**逐张比对字节确认副本确比原件更小时才读副本**；高分屏大图需核细字对齐时配「1 张适度限宽全景图 + 关键区 `1:1` 原分辨率局部裁切图」，严禁压成低清糊图、马赛克 JPEG 或缩略多宫格。
   - **③ 视频与音频（保留原生运动与音轨天赋）**：单次 `<= 8 MB` 的音视频直接用 `read_file` 原生直读，完整吸收连续动作、人声语气、配乐节奏与音画同步；大体积或需多轮复看的音视频先用 `ffprobe` 查时长与码率，再用 `ffmpeg`（`sandbox_exec` 传 `maxMemoryMB=1024`）在 `scratch/` 截取目标时段并压至合理码率且**保留所需音轨**后再直读；**仅纯台词检索或精确字幕时间点定位问题**才做音频转写或抽帧，严禁一刀切退化成纯文本/关键帧丢掉连续画面与声音信息，也严禁把几十 MB 原始长视频/音频裸塞主线每轮重传。
   - **④ PDF（实测底层机制 + 零图定位切页 + 扫描件 `150 DPI` 瘦身）**：
     - **实测机制**：宿主 `read_file` 读 PDF 时**忽略 `StartLine`/`EndLine` 参数**，会一次性将整份 PDF 全页转为视觉渲染图（约 `520 tokens/页`）并把原 PDF 二进制随全量请求体每轮重传。
     - **小件直读**：单次 `<= 10` 页且 `<= 5 MB` 直接 `read_file` 原生直吃逐页渲染图与文字层。
     - **超大 PDF 零图定位与 `scratch/` 切页**：先用 `PyMuPDF`（`fitz`）脚本只读提取 `get_toc()` 目录树与关键词命中页码完成零图定位，在 `scratch/` 切出目标页子集 PDF（跨页图表/论述须连带相邻上下文页，汇报/记录中标明原页码及跳过范围）再 `read_file` 原生直读；纯文字/矢量图表 PDF 切页后体积极小无需压缩，**仅扫描位图子集单份仍 `> 5 MB` 时**，用 `fitz` 做 `garbage=4, deflate=True` 无损清理或按 **`150 DPI` / `quality=80～85`** 重采样瘦身（**严禁压至 `72 DPI` 导致正文小字模糊不可辨**）。
     - **几十页长审分片并发**：需要通读审阅数十页长 PDF 时，按 **`8～12` 页**在 `scratch/` 切分片 PDF，并发派短命子代理各自直接 `read_file` 吃完输出精确页码结论后立即 `kill`。
   - **⑤ 批量媒体卸载与原件守恒**：`>= 4` 张连续截图、多轮改版重截对比、多段视频或多片 PDF 排查时，**必派**短命独立子代理（`invoke_subagent(TypeName="research", Model="inherit")` 或干净 `Neon XHigh`/`Carbon High`）在独立上下文直读挑刺，仅向主线返回精确文字坐标/页码结论与极少数最终定稿核验图并立即 `kill`（严禁主线把中间过程图全量重读一遍），切断主线请求体滚雪球膨胀。面向用户展示 `![...]` 与正式交付**只用原尺寸高清原件**，严禁覆盖原件或拿 `scratch/` 检视副本顶替。
3. **本地 HTML 修改后的会话缓存铁律**：`web_interact` 复用已有 `sessionId` 时，即使重传本地 `file://` URL 也可能命中旧页面缓存！每次修改磁盘上的 HTML/JS/CSS 后，**必须先 `close` 旧会话再新建会话（或执行强制无缓存刷新并核验 DOM 特征）**，确认加载的是最新磁盘代码。
4. **无头视口高度差异注意**：无头浏览器中 `window.innerHeight` 与全屏容器 `clientHeight` 可能存在差值（曾导致全屏 Three.js Canvas 底部出现黑带），全屏渲染应绑定容器 `clientHeight` + `ResizeObserver` 并在多个视口下实测。
5. **末轮改码后的全视角版本一致性**：最后一轮修改代码、材质、相机或布局后，**所有受影响的视角/页面必须重新截图并重看**；未重截的旧图绝不能混入最终交付验证清单冒充最新版成果。
6. **测试期宿主机硬件负载护栏（严防无头软光栅拖卡电脑与假基线误导）**：无头 Chromium 默认走 CPU SwiftShader 软件光栅化，直接长挂未暂停的 WebGL/3D、重度 Canvas、复杂滤镜或高频动画页会瞬间吃满全核 CPU 与 `1 GB+` 内存导致整机卡顿！对此类重渲染页截图或检查 DOM 时，**必须优先传静态确定性暂停参数（如 `?paused=1`）或首帧冻结钩子，截完当轮立即 `close` 释放会话**，严禁在改码间隙留置后台浏览器空转跑 `rAF`；确需实测动态交互时，须单实例串行、限制极短采样帧数/时长，并配合系统探针确认本机 CPU/GPU/内存水位平稳。注意无头 SwiftShader 反映的是纯 CPU 像素填充开销，仅用于核验画面、交互逻辑与暂停回收，**严禁拿 CPU 软光栅失真帧率充当真硬件 GPU 基线误导瓶颈定位**。

## 三、登录墙核验与会话资源卫生

- **本地登录态先实测与离席不阻塞**：公开模板与工具包不携带任何 Cookie、账号或浏览器资料；若接收方在本机 `web-fetcher` 中独立配置了站点持久登录态，Cookie/localStorage 文件存在时仍可能已过期——必须实际访问目标页核验正文，确认确需人工登录时再用 `web_login_browser(background=true)` 并以 `30～45s` 短轮询等待人工操作（若轮询超时确认用户暂不在电脑前，保留明确待登录入口并继续推进一切不依赖该登录页的独立实现或验证，严禁把整段工程停死），不凭搜索摘要冒充已读正文，绝不绕过验证码或付费墙。
- **只清理自建资源**：持久会话必带显式 `ownerId`（当前会话 ID），收尾时通过明确 `sessionId` 或 `closeAllForOwner` 关闭本任务自建会话与窗口，**严禁关闭借用的用户浏览器或清理共享登录态/Cookie/profile**。

## 四、聊天正文图文混排、`<agent-embed>` 微组件与 `sidecar://` 胶囊

1. **正文图文混排**：反重力 2.0 仅允许内联渲染当前对话专属 `brain/<conversation-id>/` 目录下的媒体文件；外部截图或生成图须先拷入该目录（`image-generator` 产物已默认直存此处），再用 `![图注](file:///C:/完整正斜杠路径)` 单图或 `carousel`（`<!-- slide -->` 分隔）混排展示。
2. **`<agent-embed>` 气泡交互卡片**：自包含 `.html` 写入当前对话 `brain/<id>/`（设 `UserFacing=true`），仅引入白名单 `https://www.gstatic.com/antigravity/web/dev/tailwindcss.min.js`；使用 `<body class="bg-transparent ...">` 与宿主动态注入的 `--card`、`--background`、`--foreground`、`--muted-foreground`、`--border`、`--primary` 等语义变量（**严禁在 `:root` 声明本地颜色回退值**，最小字号 `>= 12px`），内容自然高度严格压在 `< 450px`（内联视口上限 `500px`，严禁顶层设 `100vh`/`h-screen`），大型仪表盘改为侧栏独立 Artifact。
3. **`sidecar://` 面板胶囊与克制红线**：仅对本机已启用运行的侧栏面板（如 `sidecar://swarm/swarm_board/`、`sidecar://dashboard`）输出 `[面板名](sidecar://...)` 胶囊且同一视图限发一颗。**严格避免本末倒置**：两三句话或一张小表就能讲明白的事，绝不耗时手搓 HTML 微组件让用户干等。
