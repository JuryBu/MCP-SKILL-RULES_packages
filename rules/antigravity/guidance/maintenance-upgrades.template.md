# 配置维护、服务切换、备份回退与 Git 发布规范（Antigravity 2.0）

修改全局或工作区规则、MCP 配置、本机常驻服务，或执行 Git 提交推送前读取本专题。核心原则：**按常识办事——自己持续维护的仓库确认没问题就默认自己提交推送并盯绿 CI，不搞机械请示审批；真正跨边界、不可逆的例外（公开发版、改写历史、动运行中的生产服务）再稳稳确认**。

---

## 一、配置与服务切换：规范备份、隔离验证与独立回退

1. **备份集中归档，不留脏文件**：修改关键配置、规则或服务脚本前，不在目标根目录留 `.bak`、`_old`、`_copy`。统一备份到 `C:/Users/<USER>/.gemini/backups/<模块>/<日期-说明>/`（或项目内 `backups/`），附带 `manifest.json`（记录原路径、字节数、SHA256、新增文件、当地时间）和**不依赖被改组件即可独立运行的回退脚本**（如 `restore.ps1`，回退后核对 SHA256；清理新增文件时只删本次新建的文件及空目录，不盲目 `-Recurse` 误删后续积累的数据）。既有只读历史纪念归档不得修改或删除。
2. **原子替换与活对话生效闭环**：关键配置与规则一律写同目录临时文件 `<name>.tmp.<pid>` → 校验非空、UTF-8 无 BOM 纯 LF 与字节上限（规则单文件 `< 24,000 B`）→ `os.replace` 原子替换 → 确认无 `.tmp` 残留。全局规则升级装盘后，主动核查当前活跃主力开发对话的生效状态并同步关键纠偏要点，避免老会话残留旧惯性导致改了规则却看不到真实结果。
3. **运行服务先在 `%TEMP%` 隔离实测，再按最小单元稳步推进**：
   - 碰运行中的代理、交流核心、MCP 网关或常驻服务时，先在 `%TEMP%` 独立副本与独立端口跑通正常请求、异常分支、进程身份校验（按 PID + 进程名/创建时间核对后再停，不盲目 `taskkill /F`）及重启恢复链；涉及可能致模型失联的关键服务时，先验通不依赖被升级对象的独立恢复入口。
   - 按真实依赖把「开窗测试」「当前批次切换」「后续批次准备」拆开：已验通的隔离前提直接复用，趁用户离席按最小可回退单元观察达标即连推下一批，不攒大包全切，也不拿「怕弹窗/怕风险」把无依赖批次全部冻结让用户硬等。确实需要用户手工配合时，把可复制命令、预期现象与失败回退一步讲清。

## 二、Git 常识推送与多机正交署名

### 1. 按常识自然推进 Git 提交与推送（去机械审批表）

- **自己长期维护的自研仓与受托共享仓**：既然是你自己负责维护的仓库，改完核清 `git status`/`git diff` 归属、`git fetch` 远端状态、精确 `git add -- <paths>`（不用 `git add .` 混入无关改动）、脱敏干净且通过真实验收后（共享仓另按第 3 节确认串行写窗），**默认没问题就自己直接提交推送已有常规分支（含日常 `main`）并盯绿云端 CI（红灯自己修绿），彻底告别机械性地请示或等待审批**。
- **按常识才需要停手确认的少数真例外**：对外打公开发版 Tag / Release（含触发外部自动更新弹窗）、首次推送到陌生外部仓库、改写远端历史（`force push`）、推送会直接触发生产服务自动切换/部署的分支、共享仓擅建新分支/worktree/clone，或修改 `.git/config`；源码推仓本身不自动等于切换或重启本机运行服务。
- **用户明确交代只改本地 / 暂不推送 / 只读排查**：忠实停在本地，也不必反复反问要不要破例推。

> 压缩恢复或跨轮接手时，通过近况与压缩前原话直接延续常识推送，绝不因重读条文又退回「自己仓库也要机械请示审批」的老毛病。

### 2. 「宿主 × 机器角色」正交署名

在多机协作（如 `development` 与 `training`）环境中，先确认本机 `local_role`（记录于仓外 `personal-care.local.md` 及本地 `GEMINI.md`），提交时保留原绑定邮箱且不修改仓库 `.git/config`，采用命令级三层双标以便区分来源：
- 命令级显示名：`-c user.name="<GitHubName> [Antigravity 2.0 · <local_role>]"`
- Commit 标题（`<= 72` 字符）：尾标注明 **`[Antigravity/<dev|training>]`**
- 消息体末尾连续无空行附来源 Trailer：
  - `Antigravity-Agent: Antigravity 2.0 (<当前主模型可读名>)`
  - `Antigravity-Machine: <local_role>`
  - `Antigravity-Conversation: <当前稳定 conversationId>`

### 3. 共享维护仓唯一主目录串行写窗与脱敏校验

- 受托共享仓只在唯一主目录 `main` 分支串行操作，不另建分支、worktree、clone 或源码副本。
- 多维护线并行时，先完成修改、验证与脱敏，经 `communication-core` 协调串行写窗（无需用户批窗）：确认**本次交棒有效或排定写窗已轮到本线**，并实查无 `.git/index.lock`、暂存区空且 `git fetch` 远端无冲突后，自主精确暂存、提交、推送并核远端 HEAD。若对端因额度耗尽离线，按同一判据核清后也可按排定顺位推仓并记入 `reconnect-sync.md`（复联首拍补发清单与哈希）。若未轮到写窗、旧交棒已失效、上一棒仍在推、暂存区脏或远端核不清（即使此时索引锁已释放），一律保留推送这一步，其余独立验证照推，不抢写不混改。
- **双机模板与脱敏门禁**：`rules/antigravity/` 保持跨机通用（训练机专属条件规则另建 `training-machine.template.md`）。更新公开模板前运行 `./install/Test-CodexToolkit.ps1` 与 `./install/Test-AntigravityRulesProfiles.ps1`（校验双版本构建、预算余量、三层解码脱敏配合 `CODEX_TOOLKIT_PRIVATE_PATTERNS` 零私密词泄漏与隔离安装回退），并逐行看 `git diff --cached` 确认无私有路径、账号、Cookie、Token、真实对话绑定 ID 或私有覆盖文件混入；本机生效与公开仓同步分开核验、如实说明。
